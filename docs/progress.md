---

## 维护规矩（不是建议）

1. **每发一个组件版本，必须在下面的「版本节点表」加一行。**
   这条是机械的：`npm run verify` 会检查每个组件在表里最新的一行，
   是否等于该组件 `package.json` 的版本号，对不上**直接报红，发不出去**。
   实现在 `scripts/progress-log.mjs`，门禁在 `test/progress-log.test.mjs`。
2. **本仓一个仓装多个组件，各自独立发版。** 表里带 `组件` 列，
   每个组件各自按新→旧排列；**新增一个组件，就必须给它开出自己的行**，否则报红。
3. **节点表只写"这一版解决了什么"，一句话。** 展开的改动写各组件自己的
   `channels/<组件>/CHANGELOG.md`，两边不要互相抄。
4. **不要在这里记流水账。** 这里只记：**货走到哪了、规矩是什么、还欠什么。**

## 接手须知：会咬人的门禁

**规矩不写在文档里，写成会报红的测试。文档不会让构建失败。**

| 门禁 | 位置 | 撞上会怎样 |
|---|---|---|
| **发版必须更新进度表** | `scripts/progress-log.mjs` / `test/progress-log.test.mjs` | 某个组件最新一行对不上它的 `package.json` → 红；新组件没有行 → 红 |
| **三个套件各自的测试底线** | `scripts/test-baselines.json` | 通过数少于底线 → 红 |
| **加了测试必须抬底线** | `scripts/test-baseline-policy.mjs` | 通过数**多于**底线也是红——新测试不进底线就等于没保护 |
| **底线被改动要过审批摘要** | 同上，`approvedDigest` | 偷偷放宽底线 → 红 |
| **关键文件不许删 / 不许清空** | `scripts/critical-test-files.json` | 删掉护栏测试或配置 → 红 |
| **计数门禁的判决必须在 `try` 外** | `scripts/verify.mjs` | 标记和判决都写在 `try` 里，外层包一层 `catch` 就能吞掉整道门禁 |
| **入口点必须能真启动** | `test/` 下的 boot 测试 | 「装完就死」那类回归会被挡住 |

### 放行标准：150 分线

三条**同时**满足才放行，缺一不放：
①**行为对**（真机实测）②**结构对**（改病根不是贴补丁）
③**不能被无声撤销**（下一个人改坏它，测试必须报红）。

第 ③ 条是这里绝大部分测试的由来。**写完修复请自己拿刀砍一遍**：
把调用删掉、故意长出第二份实现、把判断关掉——每一刀都必须报红，否则那些绿是空的。

## 还欠什么

**一律现查，不要抄快照。** 只点名会影响你怎么写代码的：

- **两仓 `prepack` 口径相反**（本仓与 `yos-core` 的处理是反的）——**需要定一个统一口径**，一直悬着没拍。
- **本仓门禁还有能被无声关掉的入口**；同源锁在 OS 侧已机械化，这边还没铺完。
- **同一个飞书应用凭据被两台机器同时长连接**时，事件随机落一台，机器人前后自相矛盾。
  `0.1.3` 已经让这个状态**可诊断**，但"重复连接自动告警"这半条**没修、没排期**。

## 协作规矩

- **作者 ≠ 验收人。** 改动走分支，不直推 `main`；谁写的谁不验收。
- **交互路径必须单独验。** 自动验收环境没有 tty，提问会被静默跳过——
  历史上的「全绿」对这条路是**零覆盖**的（微信扫码、飞书授权都属于这条）。
