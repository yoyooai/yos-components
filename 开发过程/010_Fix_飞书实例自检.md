# 飞书实例自检

## 背景

飞书长连接不会可靠告诉单个客户端“同一个 App ID 是否还在别处连接”。当前渠道已经在启动日志和消息处理日志中记录脱敏 App ID 与主机身份，但 `yos doctor` 无法读取这份本机身份，跨机器排查仍需要人工翻日志。

## 关键决策

- 复用现有 `describeInstance()` 脱敏规则，不再创建第二套 App ID 表示法。
- 在能力声明中增加本地 health hook，输出严格 JSON：状态、脱敏 App ID、主机名、连接模式。
- Core 只接收固定形状和白名单字符；组件即使额外输出字段，也不会被 doctor 透传。
- 无法读取本机配置时明确失败，不猜测另一台机器、不联络其他主机，也不把诊断信息发给客户。

## 未采用

- 不宣称自动检测双连接。SDK 当前没有提供可依赖的全局连接冲突信号。
- 不输出完整 App ID、App Secret、配置文件路径或任意组件 JSON。
- 不新增远程探测或主机间通信。

## 自动验证

- 纯函数覆盖脱敏 App ID、主机、websocket/webhook 与未知配置。
- 包内入口测试真实启动 `hooks/health.js`，从临时 HOME 读取配置，断言完整 App ID 不出现在 stdout。
- SKILL 声明与 hook 文件存在性受测试保护。
- Core doctor 测试证明只接收 `app/host/mode` 三项，组件夹带字段不会进入诊断结果。

## 影响范围

只增加飞书能力健康检查的本机身份输出与 `yos doctor` 展示；飞书连接、收发消息、权限和客户可见行为不变。
