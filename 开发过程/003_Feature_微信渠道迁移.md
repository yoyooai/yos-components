# 微信渠道迁移

## 背景

飞书独立验收继续进行时，微信渠道按独立分支并行开发。渠道之间可以并行施工，
但必须分别锁定来源、分别验收、分别发布，不能用一个渠道的通过结论替另一个渠道
背书。

## 上游选择

- 仓库：`Tencent/openclaw-weixin`
- 标签：`v2.4.6`
- 提交：`cef0bfc390393f716903e16d50408118047f87e0`
- 许可证：MIT

Zylos 当前没有官方微信实现。腾讯官方插件是微信协议实现的一手来源，但它原本依赖
OpenClaw 宿主，因此本轮不是简单品牌替换，而是保留协议实现、重写宿主适配层。

## 关键决策

1. 保留腾讯来源、许可证、变更记录和精确提交证据。
2. 微信凭据和同步游标只保存在 `~/yos/components/weixin/`，不进入安装包。
3. 入站消息通过 YOS C4 接收合同投递，原始微信消息 ID 作为幂等键。
4. 出站回复通过独立 `scripts/send` 入口发送，不把微信逻辑写入 YOS Core。
5. 第一版只声明腾讯上游本身支持的私聊能力，不虚构群聊支持。
6. PM2 必须显式使用 Node 运行 `.ts` 入口，不依赖 PM2 对扩展名的 Bun 自动选择。
7. 服务每次启动都把微信顶层数据目录收紧为 `0700`，不能只保护账号和日志子目录。

## 否掉的方案

- 直接安装 OpenClaw 插件：会引入第二套宿主、会话和网关，不符合 YOS 分层。
- 从旧 Channels 仓复制：来源与修改历史不清，无法持续跟踪腾讯上游更新。
- 等飞书完全结束再开工：渠道组件互不依赖，串行等待没有工程收益。

## 验收边界

- 自动化覆盖来源、组件合同、扫码凭据存储、长轮询、C4 幂等投递和回复路由。
- 独立验收必须使用真实微信扫码、真实私聊、重启恢复和卸载清理。
- 验收前不合入 `main`、不登记 Registry、不对客发布。
